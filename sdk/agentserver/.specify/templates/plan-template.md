### Code Review Cadence (Constitution Principle XIII)

*Required when the spec has three or more implementation phases or user stories.*

Per Constitution Principle XIII (Continuous Code Review Discipline), multi-phase implementations MUST include code review tasks as sequencing fences interleaved with implementation, not a single end-of-PR step. This subsection identifies the review structure the implementation will produce:

- **Per-phase reviews**: list the phase boundaries (one per implementation phase or user-story phase) where a code-review agent dispatch will run. Each entry: phase name → scope focus (e.g., "Phase 4 / US1 review: stale_timeout removal completeness; no replacement knob secretly introduced").
- **Cross-phase seam reviews**: identify any phase boundaries whose hand-off is architecturally significant (e.g., a phase that introduces an API surface another phase will consume; a phase that mutates a hot-path another phase will further mutate). Each entry: A→B label → scope focus.
- **Final whole-PR holistic review**: confirms the last action before marking the PR ready for human review.

The `tasks.md` produced by `/speckit.tasks` MUST emit these review tasks as a "Continuous Code Review" phase, with each Checkpoint marker in the intervening phases annotated with `→ Run TXXX before moving to Phase Y` arrows pointing at the gating review task. BLOCKING / HIGH findings MUST be addressed before the gate clears.

If the spec has fewer than three phases / stories, this subsection states "N/A — single-phase implementation; end-of-PR review suffices."
